# ask-analytics

A public demo: a usage dashboard over a seeded workspace, plus an assistant that answers questions about it in plain English and can only answer with numbers the dashboard can derive. It is a rebuild of a pattern shipped for a client, on synthetic data.

Source of truth, in this order: `docs/SPEC.md` (what), `docs/ARCHITECTURE.md` (how), `docs/PLAN.md` (phases, gates, progress log), `docs/decisions/` (why). If code and docs disagree, stop and say so.

## Commands

- `make setup` install backend (uv) and frontend (npm) dependencies
- `make seed` regenerate `data/events.jsonl` and `data/ground_truth.json` from the fixed seed
- `make dev` run backend on :8000 and frontend on :3000
- `make check` lint, type check and unit tests for both sides, plus evals in fixture mode. Must exit 0 before any commit.
- `make evals` run the eval set against the live model (spends API credits; never run without being asked)

## Architecture rules

1. **One source of numbers.** Every number on the page and every number the assistant says comes from the lookup functions in `backend/app/lookups.py`: the five the assistant can call, plus `activity_over_time`, which feeds the dashboard's charts and is not an assistant tool. No aggregation anywhere else: not in routes, not in the frontend, not in prompts.
2. **The model never does arithmetic and never sees raw events.** It picks a lookup and a window, gets the result, and words the answer. If no lookup covers the question, it refuses and names what it can answer.
3. **Sources sit behind one interface.** `EventSource` has a file implementation now and a Mixpanel one later. Nothing outside `backend/app/sources/` knows which is in use.
4. **Time is pinned.** "Today" is `AS_OF` from the seed metadata, never the wall clock. This is what makes exact-match evals possible.
5. **The registry is typed.** A tool in the catalog without a headline event must fail the type check. Keep the test that proves it.
6. **The admin token never reaches the browser.** The frontend calls the backend from server-side route handlers only.
7. **No client vocabulary or data.** Never use names, terms, schemas or numbers from any real client system. Everything is the synthetic workspace in `docs/SPEC.md`.

## Working loop (every phase)

1. Read the phase in `docs/PLAN.md`. Do not start it until the previous gate is ticked.
2. Tests first for core logic (seed, lookups, registry, refusal behaviour). Then implement.
3. Run `make check`. Fix until it exits 0.
4. Run the reviewer agent on the phase diff. Fix every blocking finding.
5. Write the gate evidence into the phase log in `docs/PLAN.md`: the commands run and their real output. Tick the gate.
6. One branch and one pull request per phase. The description carries the plan summary and the gate evidence. Merge only when CI is green.

## Guardrails

- Never commit secrets. `.env` is ignored; only `.env.example` is tracked.
- Never edit `data/ground_truth.json` by hand. It is generated by `make seed`.
- No new dependency without one line of reason in `docs/decisions/`.
- Never weaken a test, an eval or the type check to make a gate pass. Say what is failing instead.
- Never call the live model in tests or CI. Use the fixture client.
- If a library's current API contradicts these docs, follow the library and note it in the phase log.

## Style

Python 3.12, type hints everywhere, `ruff` and `mypy --strict` on `backend/app`. TypeScript strict on the frontend. Small functions, plain names, no cleverness. Comments say why, not what.
